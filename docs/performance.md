# 첫 경기 로딩과 빌드 크기

## 2026-11-02 측정

Windows, Node 22.22.2, 현재 lockfile로 같은 프로덕션 빌드를 비교했다. 아래 값은 가장 큰 두 JS 청크의 실제 바이트 수이며 미디어 전송량이나 전체 페이지 크기는 아니다. 파일 해시는 빌드마다 달라질 수 있다.

| 청크 | 변경 전 bytes | 변경 후 bytes | 감소 |
| --- | ---: | ---: | ---: |
| `UiFeedback-*.js` (Phaser 포함) | 1,529,018 | 1,247,711 | 18.40% |
| `ArenaDuelScene-*.js` | 972,134 | 926,088 | 4.74% |
| 합계 | 2,501,152 | 2,173,799 | **327,353 bytes / 13.09%** |
| 합계 gzip | 717,490 | 656,552 | **60,938 bytes / 8.49%** |

gzip은 Node `gzipSync` 기본 설정으로 각 청크를 압축한 값의 합이다. 서버의 압축 설정이나 Vite 출력과는 다를 수 있다. 이 결과는 코드 전송·파싱 대상이 줄었다는 근거이며, 실제 첫 경기 시작 시간이 13% 빨라졌다는 뜻은 아니다. 아래 후속 실측은 별도 변경의 로딩 시간을 비교한다.

## 원인과 변경

1. **Phaser 배포본.** `UiFeedback`이라는 청크 이름과 달리 대부분은 Phaser였다. 설치된 동일 버전 3.90.0의 공식 `phaser-arcade-physics.js`를 사용해 쓰지 않는 Phaser Matter 통합을 제외했다. Canvas/WebGL과 오디오 등 사용 기능은 유지한다. 독립 시뮬레이션에서 직접 사용하는 `matter-js`는 변경하지 않았다. Phaser Matter API가 새로 필요해지면 이 alias도 재검토한다.
2. **미디어 목록.** 오디오·글꼴의 출처 및 제작 메타데이터까지 런타임 JS에 포함되어 있었다. `build/runtimeMedia.ts`가 Vite의 JSON 처리 전에 실행에 필요한 key/path/hash, duration, voice, font 필드만 남긴다. 원본 `src/assets/runtime-media.json`과 `NOTICE.md`의 출처 정보는 유지한다. 모듈 기여도 추정치는 249,986 → 57,743 bytes로 줄었다.
3. **마을 전용 텍스처 의존성.** arena에서 쓰지 않는 family 선언 경로가 `native-city-ktx2.json`을 끌어왔다. 공통 Phaser 아트 어댑터를 `PhaserFightDeps.ts`로 분리하고 arena가 직접 사용하도록 했다. 기존 `NativeCityFightDeps.ts`는 마을의 family 동작을 보존하는 wrapper로 남겼다. Cup 빌드에서 해당 JSON과 연결 모듈이 빠졌다.
4. **부팅 대기 순서.** 기존에는 전투 모듈 import가 끝난 뒤 `bootGame`의 글꼴 로딩과 Phaser 초기화를 시작했다. 이제 두 작업을 동시에 시작한다. `host-ready`는 여전히 호스트 씬 생성 시점이며, 경기 시작은 모듈·선수·씬 준비를 모두 기다린다. import 실패는 즉시 관찰하고, 기다리는 동안 종료·요청 교체·시간 초과가 발생하면 오래된 작업은 씬을 만들지 않는다.

시뮬레이션 계산, 난수 소비, seed, 선수 선택, 결과 메시지 계약은 수정하지 않았다. 사용자 입력이나 미디어를 예측해 미리 전송하는 새로운 외부 요청도 추가하지 않았다.

## 다시 측정하기

```sh
npm run analyze:build
npm run analyze:build -- bundle-report.json
```

`scripts/analyze-build.mjs`는 메모리에서 프로덕션 빌드를 만들고 상위 청크와 구성 모듈을 출력한다. 선택 인수는 전체 JSON 보고서 경로다. `dist/`를 덮어쓰거나 public 미디어를 복사하지 않는다. 생성된 보고서는 측정용 로컬 파일이며 검토 없이 커밋하지 않는다.

`bytes`와 `gzipBytes`는 최종 청크의 실제 크기다. 모듈의 `bytes`는 bundler의 `renderedLength`로, 최종 minify 전 기여도 추정치다. 모듈 크기를 합쳐 전송량이라고 보고하지 않는다. 청크 이름만으로 책임을 추정하지 말고 모듈 목록과 import 경로를 함께 확인한다.

- `npm run check`: 타입 검사, 12개 파일의 71개 테스트, 프로덕션 빌드 통과.

- `twitch-runtime-media.test.ts`: 모든 오디오 식별자·해시·길이, voice cue, 글꼴 속성 보존을 원본 목록과 대조한다.
- `twitch-arena-host.test.ts`: 모듈 지연 중 게임 부팅, 종료, 요청 교체/중복, import 실패 및 기존 연속 경기·오류 처리를 확인한다.
- Chrome에서 `npm run preview`의 내장 선수 4명으로 준결승 2회·결승·우승 표시를 확인했다. Stream view 왕복과 New cup의 iframe 제거·0/4·빈 대진·OPEN LOBBY 복귀도 확인했다. 실제 Twitch 로그인·채팅과 등록 선수 API는 이번 수동 검증에 포함하지 않았다.

큰 청크 경고는 아직 남는다. Phaser 약 1.25 MB와 arena 약 926 kB는 첫 경기에 필요한 코드가 상당 부분이며, 단순히 파일을 나눠도 총 전송·평가 비용이 사라지지 않는다. 추가 lazy import는 실제 사용 시점과 부수효과 순서를 확인한 뒤 적용한다. 경고 임계값은 올리지 않았다.

## 후속 실측: HTTP 캐시 없는 첫 경기

2026-11-02, 기준 `95da1b4`에 수동적인 User Timing 표식만 추가한 빌드와 아래 두 최적화를 적용한 빌드를 비교했다. 실제 Chrome 156/Windows에서 로컬 데모의 KUMA/Yume 첫 경기를 실행했다. **Start cup 클릭 → 부모가 첫 `bout-ready`를 받은 시점**을 측정한다. 인트로 연출이 끝나거나 첫 타격이 나오는 시간과는 다르다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 1회 | 5,840.9 ms | 5,940.6 ms |
| 2회 | 7,850.6 ms | 6,153.0 ms |
| 3회 | 6,941.1 ms | 6,009.1 ms |
| 중앙값 | **6,941.1 ms** | **6,009.1 ms (13.4% 감소)** |
| 준비 완료 때 iframe 리소스 수 | 99 | 82 |
| 완료된 iframe 리소스의 전송 본문 합 | 16,143,626 bytes | 12,445,943 bytes (22.9% 감소) |
| HTTP 캐시 적중 / 재검증 | 0 / 0 | 0 / 0 |
| 글꼴 대기 중앙값 | 208.1 ms | 1.8 ms |
| 씬 추가 → 전투 준비 중앙값 | 5,047.7 ms | 4,014.3 ms |

샘플별 단계 시간·환경·제외된 이미지 목록은 [측정 기록 JSON](measurements/2026-11-02-first-bout.json)에 보존했다. 리소스 합계는 준비 시점까지 완료된 같은 출처의 iframe 요청이며, 로비·iframe HTML·HTTP 헤더·나중에 요청한 오디오를 포함하지 않는다. `encodedBodySize` 합계이므로 JS는 gzip, WebP/WOFF2는 파일 압축 상태의 크기다.

### 측정 조건과 한계

- 프로덕션 빌드를 loopback HTTP로 제공하고 텍스트는 gzip으로 전송했다. 네트워크·CPU 속도 제한은 걸지 않았다. 운영 CDN이나 모바일 측정값이 아니다.
- 샘플마다 쓰지 않은 포트로 새 출처를 만들고 모든 응답에 `Cache-Control: no-store`를 적용했다. 같은 출처의 Resource Timing에서 캐시 적중·304 재검증이 없고 HTTP 200으로 수신했는지 확인했다. [transferSize의 의미](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/transferSize)를 따른다.
- 새 브라우저 프로세스는 만들지 않았으며 OS 디스크·폰트·GPU/드라이버·프로세스 내부 캐시는 초기화하지 않았다. 측정 중 빌드·테스트를 동시에 실행하지 않았고 게임 문서가 숨겨진 샘플은 없었다.
- 실제 기록된 부모 화면 너비는 1897 CSS px, DPR은 약 1.35였다. 브라우저 UI에 따라 높이는 973–1035 px로 달라졌다. 일반 모드의 경기장은 너비 기준 16:9로 정해져 이 높이 변화에 따라 크기가 바뀌지 않는다. 초기 탐색용 3회는 최종 비교에서 제외하고 비교군 3회를 다시 수집했다.
- 표본이 작고 변경 전 편차가 있다. 1회차는 오히려 99.7 ms 느렸으므로 모든 실행이 13.4% 빨라졌다고 해석하지 않는다. 중앙값과 리소스 감소를 함께 본다.
- 비교 배치 이후 전체 컵 동작 확인에서는 같은 빌드·새 출처·HTTP 캐시 적중 0으로 **1,338.9 ms**도 관측했다. 씬 준비는 513.8 ms였으며, 준비 전에 완료된 리소스가 81개/12,135,269 bytes였다(`net.webp`는 이 시점 합계에 없었다). 브라우저/시스템 상태에 따른 차이를 완전히 통제하지 못했으므로 이 추가 관측도 JSON에 보존하며, 위 13.4%를 안정적인 환경 독립 개선율로 취급하지 않는다.

### 실측으로 수정한 병목

1. **마을의 전방향 이동 이미지 대기 제거.** 경기장은 좌우만 그리는데 preload와 `NativeCityKumaView.artReady`가 KUMA/Yume의 앞·뒤·대각선 idle/walk까지 기다렸다. `arenaGaitSheets`를 두 경로가 함께 사용해 실제 좌우 클립과 기존 mirror fallback만 고른다. 17개 이미지, 3,697,742 bytes가 첫 경기 요청에서 빠졌다. 마을용 분기와 원본 파일은 유지한다. 9종 내장 팩, 기존 마을 경로, 좌우 전용 registered 형태의 회귀 테스트를 추가했다.
2. **글꼴 발견 시점 앞당김.** `fighter.html`에서 실제 사용하는 세 WOFF2를 `as="font"`와 `crossorigin`으로 preload한다. 기존에는 엔진 실행 후에야 bold/lettering 요청을 발견했다. 같은 글꼴·굵기·화질을 유지하며, 실측에서 중복 요청 없이 부팅의 글꼴 대기가 줄었다.

선수 pack 요청은 기준 측정에서 수십 ms였다. 이번에는 이를 위해 호스트 요청 순서를 다시 바꾸지 않았다. 시뮬레이션·난수·결과 처리도 변경하지 않았다. User Timing의 `oddbout:*` 표식은 로컬 브라우저 성능 기록이며 네트워크로 전송하지 않는다. 측정 서버에서만 별도 probe가 로컬 JSONL을 수집한다.

### 재현 절차

```sh
npm run build
npm run measure:first-bout -- --ports=5186,5187,5188 --label=before --out=first-bout-report-before.jsonl
```

1. 콘솔에 나온 `127.0.0.1` URL을 열고 **Try it solo → Try without Twitch → Fill all 4 slots → Start cup**을 직접 조작한다. 공개 선수 API가 없는 환경에서 내장 선수로 측정한다.
2. 화면의 측정 결과와 서버 JSONL 기록을 확인한다. 첫 경기의 seed는 기존처럼 생성되며, 측정기가 게임 명령·난수·결과를 주입하지 않는다.
3. 이전 탭을 닫고 다음 포트에서 반복한다. 화면 너비·DPR·일반 모드·가시성을 유지하고 다른 무거운 작업을 피한다. 관측된 크기는 JSONL의 viewport로 확인한다.
4. 서버를 종료하고 코드를 변경·검증·재빌드한다. **새 포트**와 별도 출력 파일로 같은 횟수만큼 반복한다.

```sh
npm run measure:first-bout -- --ports=5190,5191,5192 --label=after --out=first-bout-report-after.jsonl
```

서버는 `127.0.0.1`에만 바인딩한다. `--dir=경로`로 보관한 이전 `dist`를 제공할 수도 있다. 실행 중에는 파일을 메모리에 보관하므로 재빌드 시 서버도 다시 시작한다. probe·측정 배너·수집 endpoint는 프로덕션 산출물에 들어가지 않는다. raw JSONL은 로컬 진단용이며 `.gitignore`의 기본 파일명 패턴을 따른다. 결과를 커밋할 때는 위 기록처럼 환경과 요약치를 검토해 별도로 보존한다.

### 후속 검증

- `npm run check`: 13개 파일의 91개 테스트·타입·프로덕션 빌드 통과. 측정 서버와 probe의 Node 구문 검사도 통과했다.
- 개선 빌드의 실제 Chrome 로컬 데모에서 두 준결승·결승·우승 표시와 New cup의 0/4·빈 대진·OPEN LOBBY 복귀를 확인했다. 실제 Twitch 인증/채팅과 등록 선수 API는 이번 수동 검증 범위에 포함하지 않았다.
- 앞선 장시간 검증에서는 결승 진행 중 오류가 한 번 발생했다. 당시 원문 오류를 기록하지 않아 원인을 확정하지 못했다. 호스트는 240초 벽시계 제한을 적용하지만 숨겨진 탭의 시뮬레이션은 멈추므로 이 경로가 가능한 원인이다. 측정 probe는 이후 모든 경기 오류 원문·가시성 이력을 기록하도록 보강했다. 새 전체 컵에서는 오류 없이 세 결과를 받았다. 기존 가시성·타임아웃 정책은 변경하지 않았다.

### 남은 비용과 마을 코드의 범위

마을 화면의 진입점이나 `VillageScene`은 Cup 빌드에 없다. 하지만 원본 게임에서 공유한 전투 효과·진행도·퀘스트·이동 데이터의 일부 import는 남아 있다. `village`라는 경로명만 보고 일괄 삭제하면 경기 표현이나 공유 상태 코드까지 손상할 수 있다. 전투기용 방향 선택처럼 실제 소비 경로를 기준으로 분리한다.

이번 개선 후에도 첫 경기 리소스가 약 12.45 MB이고 씬 준비 구간은 중앙값 약 4.01초다. 추가 후보는 필요한 전투 시트의 전송/이미지 디코드/텍스처 생성 비용, Phaser 실행과 씬 초기화, 남은 마을 전용 데이터 참조다. 현재 측정은 씬 준비 구간을 이 내부 단계들로 완전히 분리하지 않았으므로 특정 하나가 4초를 모두 차지한다고 단정하지 않는다. 시트의 해상도·프레임을 낮추거나 READY/FIGHT 연출을 생략하는 변경은 하지 않았다.
